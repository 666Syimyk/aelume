# 01. Назначение, границы и исходные допущения

## 1.1. Определение

HoloCall Cube — компактный настольный терминал двусторонней аудио- и видеосвязи, отображающий полученный видеопортрет с удалённым фоном в специальной оптической сцене. Результат представляет собой **виртуальное отражённое изображение**, а не свободно висящее в воздухе трёхмерное световое поле. Пользователь с Android-смартфоном может позвонить на куб, даже если у него нет второго куба. Сам куб в D2 должен иметь камеру и микрофон для обратной связи.

**Основная задача D0:** доказать наблюдаемый и повторяемый оптический эффект с заранее записанным и живым портретом. **Основная задача D1:** доказать рабочий двусторонний разговор между разными сетями. **Основная задача D2:** объединить сцену, вычисления, интерфейс, питание, приватность, запуск, обслуживание и пилотные испытания в самостоятельном устройстве.

## 1.2. Что сознательно НЕ входит в обязательный объём

Не входят в D0–D2 как критерии приёмки: настоящая светопольная голограмма, обзор с корректной глубиной на 360°, реалистичный затылок по единственной фронтальной камере, гарантированная работа под прямым солнечным светом, неограниченное число участников, автономная батарея, универсальные iOS-клиенты, нейронный цифровой двойник, голосовой ИИ-ассистент, незаметная запись разговоров, распознавание эмоций.

Исследовательская демонстрация этих направлений допускается только как изолированный EXP-проект без блокировки основной коммуникационной функции. Запись видео по умолчанию запрещена; любые будущие механизмы записи требуют отдельного PRD, модели согласия и юридического анализа.

## 1.3. Классы пользователей и границы доверия

Роли: **владелец куба**, **разрешённый собеседник**, **локальный пользователь без аккаунта в D0/D1**, **оператор поддержки**, **администратор инфраструктуры**, **заводской тестировщик**. Ни поддержка, ни администратор не получают доступ к содержимому личных разговоров через штатную панель. Сервер получает только необходимые сигнализационные и эксплуатационные метаданные. Персональные ключи, токены, конфигурация Wi‑Fi и профили аватара разграничены по владельцам и устройствам.

Исходные допущения: домашняя сеть 2,4/5 ГГц определяется выбранным радиомодулем; внешнее питание; один основной зритель; indoor use; нормальный акустический разговор; базовая конфигурация с одной оптической сценой. Поддержка других условий определяется после лабораторных испытаний.

# 03. Функциональная архитектура системы
**Участники:** смартфон отправителя ↔ защищённая серверная инфраструктура ↔ HoloCall Cube. Секреты аккаунта и токены выдаются отдельным API; видеомедиа идёт через WebRTC direct/SFU/TURN в зависимости от согласованной топологии. Операционный сервер не должен превращаться в неявный источник персональных записей.

**Контуры обработки:** (A) Android Camera → сегментация → композиция чёрного фона → Encoder; (B) микрофон → AEC/NS/AGC в согласованном аудиостеке → Opus; (C) WebRTC receive → decoder → compositor → GPU output → дисплей/отражатель; (D) обратная камера куба → encoder → Android; (E) управление состояниями/кнопками/сопряжением/обновлениями независимо от AI-процессора.

**Режим отказоустойчивости:** при неисправности сегментации разрешён исходный видеокадр или видео «камера недоступна»; при неисправности видео аудио продолжает работать; при отсутствии сети UI отражает достоверное состояние и предлагает повторить; при потере питания после загрузки система возвращается в безопасную готовность без преждевременного открытия микрофона.

# 04. Сквозные сценарии и состояния

## 4.1. Сценарий SC-01: первый локальный оптический эксперимент

Инженер запускает тестовую сцену и измеряет геометрию виртуального изображения; последовательно устанавливает тестовый паттерн, портрет с волосами/очками, изображение с тёмной одеждой и динамический клип. Для каждого режима сохраняются положение экрана, угол отражателя, освещение, изображение с камеры на уровне глаз наблюдателя, видимый размер портрета и субъективная оценка узнаваемости. Нельзя исключать неудачные измерения: они фиксируются вместе с условиями.

## 4.2. Сценарий SC-02: звонок со смартфона на куб

Отправитель открывает приложение → выбирает доступный куб/контакт → запрашивает звонок → сервер проверяет разрешение → куб показывает приглашение → локальный пользователь физически принимает вызов → обе стороны подтверждают медиа-готовность → аудио и видео запускаются → при завершении ресурсы освобождаются и токены инвалидируются. Если принять не успели, состояние истекает по таймауту и медиа не стартует. Дублированное приглашение и повторное нажатие не создают вторую сессию.

## 4.3. Сценарий SC-03: отказ камеры и плохая сеть

Видеообработка перестаёт выдавать маску → клиент переходит на исходный видеопоток или честно показывает сообщение об отсутствии видео → аудиосессия не разрывается только по причине AI. При падении полосы сначала уменьшаются разрешение и частота кадров; при длительном отсутствии актуальных кадров показывается статус. При сети с потерями ICE restart или controlled reconnect разрешён с ограниченными повторами. UI никогда не показывает заведомо старый кадр как живую трансляцию.

## 4.4. Сценарий SC-04: смена владельца, потеря телефона, утеря куба

Утерянный смартфон удаляется из доверенных сессий, его токены и доступ к звонкам отзываются; устройство получает запрос на разрыв доверия. Локальный factory reset требует физического подтверждения в течение ограниченного времени и удаляет ключи, Wi‑Fi, профили пользователя, разрешения контактов и калибровку только в пределах утверждённой политики (заводской профиль оптики может быть сохранён в отдельном защищённом разделе). Старый владелец утрачивает контроль. Учётный сервис отражает операцию в аудите без содержания звонков.

# 06. Оптическая инженерия и геометрия

## 6.1. Математическая постановка

Для плоского отражателя проектируется виртуальная плоскость изображения — зеркальное отражение исходной плоскости дисплея относительно плоскости отражателя. В CAD координаты задаются в единой правой системе: ось X горизонтально к зрителю, Y вертикально, Z от передней стенки вглубь; альтернативная система допустима только при явном описании преобразований. Отражённая координата точки **p** относительно плоскости через **p₀** с единичной нормалью **n**: `p' = p − 2 n (n · (p − p₀))`. Это геометрическая модель идеального плоского зеркала, а не гарантия качества визуальной сцены.

Необходимо рассчитать трассировку характерных лучей из четырёх углов дисплея к каждому из выбранных положений глаз зрителя. Отдельно рассмотреть толщину пластин, двусторонние отражения, коэффициенты R/T при рабочем угле, поляризацию исходящего света, отражение от кожуха, кадрирование и габариты рамки. Экранную яркость не смешивать с яркостью виртуального изображения: расчёт и измерения вести отдельно.

## 6.2. Параметры, подлежащие фиксации

В рабочей модели задаются: диагональ и активная область экрана, рабочее разрешение, яркость во времени, угол/толщина/покрытие каждой пластины, местоположение виртуальной плоскости, видимый размер портрета, дистанции до глаз, допустимый горизонтальный и вертикальный диапазоны взгляда, внутренние поглощения, отражения внешней среды и углы камеры. Изначальные размеры 6–8 см и 10–12 см высоты портрета — **исследовательские варианты**, а не серийные габариты.

# 07. Экран, видеовывод, цвет и калибровка

## 7.1. Выбор дисплея

Конкретная OLED/LCD-панель выбирается по доступности, цене, интерфейсу, аппаратной поддержке, устойчивой яркости, правильному уровню чёрного, термонагрузке, мерцанию, углу работы, запасу ресурса и равномерности. # 09. Электропитание, аппаратная платформа и тепловой режим

## 9.1. Топология питания и безопасность

Для D2 базовая схема — внешний сертифицированный адаптер с безопасным выходным напряжением, защитой от перенапряжения, перегрузки и короткого замыкания, защищённый вход питания, силовая распределительная плата и раздельные шины для SoM, экрана, камеры, аудио и индикаторов. Конкретные номиналы и классы защиты определяются аппаратным проектированием и регуляторной оценкой. Не использовать открытые клеммы сетевого напряжения внутри пользовательского корпуса в прототипе без специализированного проекта и проверки безопасности.

Проектные расчёты включают worst-case мощность, пусковые токи, пульсации, просадки на кабелях, режим питания после brownout, ESD, EMI, защиту портов и условия эксплуатации. Силовая компоновка исключает проникновение шумов экрана и DC/DC в аудиотракт.

## 9.2. Выбор вычислительной платы

Никакой SoM не утверждается только по числу TOPS или частоте CPU. Нужно проверить: аппаратный encoder и decoder для согласованных кодеков, возможность zero-copy кадра из камеры к GPU/encoder, экосистему драйверов, стабильность Wi‑Fi, аппаратный watchdog, доступность образцов минимум на два инженерных цикла, документооборот поставщика и реальные тесты температуры. В D1 внешний ПК допускается и предпочтителен для ускорения поиска архитектурных ошибок.

# 10. Камера, микрофоны, динамик и аудиопроцессинг

## 10.1. Концепция медиасенсоров

Камера куба смотрит в область основного пользователя и находится как можно ближе к ожидаемой линии взгляда, но не должна загрязнять оптическую сцену отражениями. # 12. AI Live Portrait и обработка кадров

## 12.1. Контракт видеокадра и тракта сегментации

Вход: `frame_id`, `capture_time_monotonic`, `width`, `height`, `rotation`, `color_space`, `pixel_format`, `camera_facing`, `crop_rect`. Выход: маска человека и confidence, `model_version`, `processing_time_ms`, timestamp исходного кадра. Выходная композиция должна сохранять согласование ориентации и не менять порядок цветов/alpha. Компонент не вправе незаметно превращать лицо в новый синтетический образ в Live Portrait.

**Поведение на границах:** при неудаче inference используем последнюю маску только в ограниченном промежутке, затем fallback. При слишком большом рассогласовании времени между маской и кадром маска отбрасывается. Ограниченный буфер в режиме realtime важнее гарантированного расчёта каждого кадра; перегруженный обработчик пропускает кадры и записывает метрику. Это соответствует особенностям асинхронной сегментации в MediaPipe: busy pipeline не обязан принять каждый новый кадр.

## 12.2. Алгоритм композиции

Преобразуем исходный кадр в унифицированную ориентацию; получаем маску `α∈[0,1]`; фильтруем шумы на границе, учитывая волосы/очки; выполняем альфа-композицию на чёрном фоне `C_out = α·C_rgb + (1−α)·(0,0,0)` в согласованном цветовом пространстве; применяем кадрирование с гистерезисом и ограничением скорости изменения масштаба; передаём GPU surface в видеоэнкодер. Маска не должна превращать тёмную одежду в отсутствующую часть человека. Слишком агрессивное размытие/«улучшение лица» запрещено без явно обозначенного режима.

# 13. Медиасвязь, кодеки, ICE и адаптация качества

## 13.1. Архитектура связи и время

Используется поддерживаемая реализация WebRTC; signaling выполняется отдельным сервисом/SDK. Для согласования ICE необходимы STUN и TURN; relay-доставка обязательна в сетях, где прямой путь недоступен. Контроль доступа к комнате осуществляется сервером приложений с короткоживущими подписанными полномочиями. E2EE D2 не считать реализованным, пока не доказаны установка ключей на обоих концах и невозможность расшифровки промежуточным узлом. TLS/DTLS-SRTP сами по себе не равны E2EE относительно SFU.

Статистика собирается отдельно по аудио и видео: RTT, jitter, loss, bitrate, encode/decode time, rendered fps, freeze count, selected ICE candidate pair, TURN usage. End-to-end motion-to-photon измеряется **внешним синхронизированным методом**, потому что метрика getStats не даёт напрямую всей задержки camera→display. Декодированный кадр с истёкшим сроком актуальности сбрасывается, чтобы избежать «накопления прошлого».

## 13.2. План адаптации

Качество задаётся предельными профилями для утверждённого устройства (например, варианты 720p/30, 540p/24, 360p/15 как **кандидаты для теста**, не обязательные возможности каждой камеры). Первым уменьшается битрейт и/или разрешение видео, затем fps, при необходимости видео временно выключается; аудио получает приоритет. Возврат качества должен иметь временной гистерезис и ограничение частоты переключений. Любая автоматическая смена режима фиксируется событием с причиной.

# 14. Backend, API, распределённые события и хранение

## 14.1. Логическая серверная структура

Рекомендуемые сервисы в пределах разумной сложности: `identity/auth`, `devices/pairing`, `call-orchestrator`, `signaling/media-provider adapter`, `notifications`, `config/ota`, `telemetry`, `admin/support`. В начале их можно реализовать в одном backend с чёткими модулями (modular monolith), а не немедленно разносить по микросервисам. База PostgreSQL используется только там, где требуется сохранение состояния. Краткоживущие токены сеансов и антиабузные счетчики хранятся с TTL в подходящем хранилище; выбор Redis не является обязательным.

Вызов имеет `call_id`, `caller_id`, `callee_id/device_id`, `created_at`, `expires_at`, `state`, `version`, `correlation_id`; переходы выполняются атомарно, с CAS/optimistic concurrency, чтобы повторная доставка не создавала гонок. Все серверные времена — UTC ISO 8601; время медиа захвата — монотонные локальные часы с описанным преобразованием. Персональные ID логируются в псевдонимизованном виде, если отладка не требует точного разрешённого контекста.

## 14.2. API-подход и ошибочные ситуации

Внешний протокол: HTTPS JSON REST с OpenAPI 3.1, WebSocket/event stream для управляемой сигнализации или модель, определённая выбранным RTC-провайдером. Сервер не принимает произвольные номера устройства как доказательство права: аутентификация привязывается к аккаунту, разрешению и фактическому владению устройством. Все create endpoints используют `Idempotency-Key` и согласованный TTL. Ошибки возвращают `code`, `message`, `request_id`, опционально `retry_after`; не раскрывают «существует ли такой частный аккаунт», если это помогает перебору.

**Предлагаемые REST-контракты:** `POST /v1/auth/...`, `GET /v1/devices`, `POST /v1/pairings`, `POST /v1/pairings/{id}/confirm`, `POST /v1/calls`, `POST /v1/calls/{id}/accept`, `POST /v1/calls/{id}/decline`, `POST /v1/calls/{id}/end`, `POST /v1/calls/{id}/join-token`, `GET /v1/health`, `POST /v1/device/reports`, `POST /v1/device/updates/check`. Маршруты являются предлагаемой схемой и утверждаются через ICD до кодирования.

# 15. Идентификация, сопряжение и жизненный цикл устройства

## 15.1. Сопряжение без слабого PIN-кода

Для production устройство имеет уникальный идентификатор и криптографическую личность (ключ/сертификат или эквивалент). При первом запуске владелец проходит короткий процесс локального подтверждения: QR или временный код содержит только короткоживущий одноразовый challenge/ссылку, подтверждение на корпусе переводит устройство в pairing window; backend связывает учётную запись с device_id по результату подтверждённого challenge. Сам по себе напечатанный на корпусе номер, известный QR или serial number не доказывает владение.

Потеря соединения в процессе pairing не должна оставлять «полупривязанное» устройство. Повторное сопряжение после factory reset отзывает старые grants. Секреты Wi‑Fi доставляются только по проверенной безопасной линии (например, защищённый BLE provisioning или первоначальный локальный канал по архитектурному решению), никогда не передаются как открытая публикация. Не выбирать BLE/SoftAP как неизменяемую технологию до проверки на выбранном SoM.

# 16. Устройство: ОС, службы, состояние, IPC

## 16.1. Внутренняя декомпозиция

Предлагаемая архитектура автономного runtime: `device-supervisor` контролирует состояния и watchdog; `media-client` поддерживает WebRTC; `render-daemon` выводит сцену; `input-daemon` читает физические кнопки и аппаратный mute; `network-manager` отвечает за Wi‑Fi, DNS и часы; `calibration-manager` валидирует профиль; `update-agent` выполняет безопасное OTA; `telemetry-agent` публикует обезличенную диагностику. На малом SoM модули могут быть процессами или сервисами в одном приложении при сохранении независимых контрактов.

Состояния: `BOOT` → `UNPROVISIONED`/`READY` → `RINGING` → `CONNECTING` → `IN_CALL` → `RECONNECTING` → `ENDING` → `READY`; поперечные состояния `MUTED`, `NO_NETWORK`, `UPDATE_PENDING`, `THERMAL_LIMIT`, `FATAL_SAFE`. Состояние `MUTED` — отдельная аппаратная истина, не заменяет состояние звонка. Любые таймеры определены монотонными часами. По переходам составляется таблица enter/exit side effects и invariant.

## 16.2. Детерминированность и восстановление

В системном журнале обязательны `transition_from`, `transition_to`, `reason`, `event_id`, `monotonic_timestamp`, `firmware_version`, `call_id_hash`. При повторе событий переход должен оставаться детерминированным. Сервис не имеет права автоматически включать удалённый микрофон или отвечать на звонок после перезапуска. Crash-loop ведёт к безопасному диагностическому состоянию, а не к бесконечным перезапускам и перегреву.

# 17. Кибербезопасность, приватность и модель угроз

## 17.1. Классы активов и противников

Активы: голос и видео в реальном времени; E2EE session key; идентификаторы и контактные связи; Wi‑Fi credentials; криптографические ключи устройств; подписанные firmware; журнал вызовов и IP-адреса; персональные аватары и исходные фото (если когда-либо появятся). Противники: неавторизованный звонящий, вор или владелец ранее привязанного телефона, сосед в Wi‑Fi, злоумышленник с доступом к серверному токену, скомпрометированный администратор, физическое вмешательство в устройство, злонамеренная модификация обновления.

STRIDE анализ включает spoofing (подмена куба/участника), tampering (изменение прошивки/калибровки), repudiation (отрицание удаления/смены владельца), disclosure (утечка ключа/кадров), denial of service (flood звонков/TURN), escalation (поддержка получает роль владельца). Для каждого сценария составить abuse case, контроль и проверку; оценки CVSS и рисков привязать к контексту, не только к числу.

## 17.2. Data minimization и криптография

Шифрование на транспорте для REST/WebSocket и SRTP обязательно; это не гарантирует E2EE относительно SFU. Ключи E2EE должны создаваться и доставляться с криптографическим связыванием подтверждённых участников; серверная выдача одного общего ключа через API без модели угроз может допускать доступ сервера к медиа и не соответствует строгому обещанию «сервер не видит разговор». Конкретный протокол key agreement и ротации — **ADR-SEC-01 (TBD)**, до его утверждения запрещено маркировать production как E2EE. При потере телефона предусмотрены revocation и rekey.

Privacy policy и retention утверждаются до пилота с учётом применимого законодательства Кыргызстана и страны обработки данных. Серверные логи не содержат паролей, сырых изображений, голосовых данных, биометрических шаблонов, токенов и приватных ключей. Показатели качества агрегируются и псевдонимизируются. Аналитика не заменяет пользовательское согласие.

# 18. Обновления, конфигурации, наблюдаемость, поддержка

## 18.1. OTA: двусторонняя безопасная схема

Устройство опрашивает update manifest с каналом (`dev`/`staging`/`pilot`/`production`), версией, firmware/hardware compatibility, размером, SHA-256 и криптографической подписью. Установка проводится с контролем питания и места на диске; в предпочтительной архитектуре используется A/B-раздел и подтверждение boot success после self-test. Если платформа не поддерживает безопасный A/B, перед пилотом требуется равноценный проверенный rollback-алгоритм. Для ядра/firmware и AI-моделей должны быть независимые журналы версий и отката.

Обновления откладываются при активном звонке, не изменяют аппаратный mute, сохраняют совместимую калибровку и позволяют определить причину неудачи. При несовместимости нового формата калибровки миграция выполняется атомарно с резервной копией.

## 18.2. Telemetry и поддержка

Метрики разделяются на технические (температура, CPU/GPU, encode/decode/fps, network loss, ICE state, power reboot reason), продуктовые агрегаты (успешный вызов/отказ/продолжительность) и security events (несанкционированная попытка, сбой подписи, revocation). Никакие сырые аудио/видео и профили лиц не отправляются как телеметрия. Метрики снабжаются временным контекстом, revision, release channel, coarse network type; избегать включения персональных контактов и точных IP в долгосрочную аналитику без отдельного основания.

Пользователь должен видеть, какие данные собираются, и иметь ясный механизм обращения в поддержку. Диагностический пакет передаётся по явно инициированному действию и проходит redaction до отправки.

# 20. Нефункциональные показатели, бюджет задержек и условия измерения

## 20.1. Принципы задания численных порогов

Порог является договорным только после утверждения одной из категорий: **Ц** — цель испытания (target), **П** — предварительная граница проектирования, **Н** — нормативный предел внешнего стандарта (указывается отдельно), **TBD** — не определён. ## 20.2. Сквозной бюджет времени

Бюджет следует рассчитывать не одной оценкой, а разбиением `capture + preprocess + segmentation + compose + encode + uplink + network + jitter buffer + decode + compositor + display scanout + optical presentation`. Для аудио аналогично `capture + AEC/Opus + network + jitter + decode + DAC/speaker`; AV синхронизация оценивается относительно этих двух цепочек. На первом стенде не фиксировать произвольные значения составляющих — инженер должен измерить и заполнить распределение (median/p95) для каждого блока.

Для доверительного измерения используйте LED/timecode target и высокоскоростную съёмку/внешнюю синхронизацию, когда доступно. Отдельно указывайте погрешность, fps камеры-измерителя, способ воспроизведения и выбранные события «начало движения» и «начало отображения». RTT из WebRTC не является временем motion-to-photon.

# 22. Протоколы данных, интерфейсные контракты и примеры

## 22.1. Общие правила сериализации

Во всех API используются стабильные идентификаторы строкой (например, UUIDv7/UUIDv4 по утверждённой схеме), UTF-8, стандартные ошибки, версионность `v1`, UTC с явным `Z` для календарного времени; размеры и геометрия в физически определённых единицах. Метки media timestamp работают на монотонном локальном clock и не должны быть напрямую сравнены с UTC без синхронизации. Поля, которых нет в контракте, по умолчанию отвергаются на boundary, если этот выбор совместим со стратегией расширения протокола.

Имена маршрутов ниже — **эталонные примеры для проектирования**, не обещание готового сервера. OpenAPI, JSON Schema и protobuf/JSON event specifications нужно сгенерировать из единого источника в репозитории, покрыть contract tests и закрепить версию. Матрица версий Android/device/backend определяет совместимость. Backend не должен доверять `caller_id`, переданному клиентом как независимому утверждению личности.

```http
Idempotency-Key: 9c0b75a4-...
Content-Type: application/json

{
  "callee_device_id": "dev_d42c...",
  "media_mode": "live_portrait",
  "client_request_id": "req_01..."

```

```json
{
  "call_id": "call_01...",
  "state": "ringing",
  "expires_at": "2026-10-31T06:00:30Z",

```

**Правила:** `callee_device_id` проверяется по ACL; `media_mode` не позволяет включить неподдерживаемый экспериментальный режим; `expires_at` выдаётся сервером; повтор `Idempotency-Key` в ограниченном окне возвращает тот же результат. Join token выдаётся только после проверки личности и права; нельзя сохранять его в журналах.

# 23. Проверка и валидация: методика инженерных измерений

## 23.1. V-model и матрица методов

Каждое требование имеет тип доказательства: `I` — inspection (осмотр/аудит), `A` — analysis (расчёт), `T` — test (измерение/автотест), `D` — demonstration (демонстрация в штатном сценарии). Нельзя принимать P0 по формулировке «работает на моей машине» без повторяемого теста. QA связывает результаты с ID требования и test-case, указывает версию software/firmware, аппаратную ревизию, среду, входные данные, дату, операторов, исходные результаты, pass/fail и найденные дефекты.

## 23.2. Физический оптический стенд и порядок замеров

Тестовая камера на штативе с фиксированной выдержкой и балансом белого (либо задокументированным авто-режимом) установлена в определённой позиции глаза. Источники света и поверхности стен описаны; люксметр измеряет освещённость в точках по карте. Для всех материалов повторяются одинаковые сюжеты. Изображение человека оценивается при нескольких высотах глаз, дистанциях и горизонтальных смещениях. Результат — матрица видимости, паразитных отражений, размера лица, узнаваемости и выбор геометрии на G0.

Пример сетки координат (настраивается под размер): дистанции 0,5/0,75/1,0 м; x-смещения −20/0/+20 см; уровни глаз относительно центра сцены −10/0/+10 см. Эти числа — стартовые точки эксперимента, не заявленная зона обзора изделия.

## 23.3. Сеть и сценарии деградации

Матрица: одинаковая LAN; разные домашние Wi‑Fi; мобильный интернет Кыргызстана; NAT с relay-only; loss 0/1/3/5%; jitter 0/20/50 мс; принудительная полоса 0,5/1/2/5 Мбит/с; переключение Wi‑Fi ↔ мобильная сеть; disconnect 5/15/60 секунд; повторные попытки; симметричное ограничение трафика. Значения являются *стимуляторами*, а не гарантированными сетевыми условиями. Конкретные комбинации отбираются через pairwise и worst-case. Обязательно отдельно оценивать качество голоса, длительность reconnect, p50/p95 задержки и число freeze событий.

## 23.4. Звук и мимика

Испытывать: двусторонняя речь, шёпот/тихую речь, шум вентилятора, отражающие помещения, повышенную громкость, аппаратный mute, закрытый микрофон. Ролики для AI включают разные волосы, очки, руки возле лица, неоднородное освещение, частичное закрытие лица, второе лицо, быстрый поворот, нестабильный фон, низкий контраст одежды. Оценку качества компоновки делать до видеокомпрессии и после неё; сохранять синтетические/разрешённые эталонные клипы с лицензиями на использование.

## 23.5. Reliability, security, factory и user acceptance

Протоколы: серия 100 звонков; 20 reboot; 2h continuous; затем soak; повреждённый конфиг; полная память/диск; отключение камеры; отказ TURN; отозванный токен; повтор pairing; повреждённая прошивка; сбой питания при OTA; сервисная сборка; транспортировка; user task success. Коммерческие сертификаты и испытания соответствия проводят уполномоченные лаборатории по отдельной утверждённой регуляторной матрице. Предварительные лабораторные тесты не являются сертификатом.

# 25. CI/CD, репозиторий, код и инженерная документация

## 25.1. Организация исходных текстов

Рекомендуемая структура monorepo: `/apps/android`, `/apps/device-runtime`, `/services/backend`, `/packages/protocol`, `/packages/security-contracts`, `/infra`, `/hardware/ee`, `/hardware/mechanical`, `/hardware/optics`, `/research/avatars`, `/tests/e2e`, `/tests/fixtures`, `/docs/adr`, `/docs/spec`, `/docs/runbooks`. Разделы hardware не должны хранить секреты поставщиков. CI запускает static lint, unit test, schema validation, license/SBOM scan, API contract tests, security scans и сборку версионированных артефактов. Привязка каждого коммита к требованию/issue не должна быть искусственной, но серьёзные изменения должны иметь tracking и code review.

Приложения и OTA собираются воспроизводимо (lockfiles, версии компиляторов, build manifest). CI не может выпускать production артефакт с debug flag, hardcoded secrets и отключённой проверкой подписи. Для тестовых видео использовать согласованный датасет с разрешением владельца контента; не публиковать реальные личные записи в открытый репозиторий.

# 26. Промышленная подготовка: EVT, DVT, PVT и EOL

## 26.1. Этапы физических образцов

`EVT` (engineering validation) подтверждает работу функции и базовой электроники/оптики, даже если корпус ещё распечатан. `DVT` (design validation) проверяет геометрию, тепловой режим, конструктивную безопасность, EMC pre-compliance, упаковку, сборку и доступность сервиса на близкой к итоговой конструкции. `PVT` (production validation) подтверждает процесс сборки на малой партии, выход годных экземпляров, контроль поставщиков и процедуру конечного тестирования. Смешивать единичный лабораторный стенд с PVT недопустимо.

## 26.2. Заводской End-of-Line (EOL)

На каждом устройстве заводской тест выполняет: визуальный осмотр, сверку BOM и ревизии платы, проверку serial/device cryptographic identity, диагностику питания, кнопок и аппаратного mute, тест микрофона/динамика тестовыми сигналами, камеры, дисплея, цветового и геометрического шаблона, Wi‑Fi соединения, запуска firmware, безопасности обновлений и sanity-check калибровки. Результат связан с серийным номером и версией test fixture. Для случая провала определён маршрут ремонта/rework, после которого выполняется полный повтор EOL, а не выдача «условно годен».

## 27.1. Граница применимости

Для пилотной площадки в Кыргызстане требуется отдельная регуляторная матрица: классификация конечного прибора, внешнего источника питания, радиомодуля, электромагнитной совместимости, обращения с электронными компонентами, маркировки, гарантийных обязательств и персональных данных. Дополнительно проверить разрешённые Wi‑Fi полосы/мощности, сертификационные документы модулей, маркировку, инструкцию безопасности и условия использования. Формальное решение о соответствии подписывает уполномоченный специалист на основании действующего законодательства и конструкции. В этом ТЗ нет утверждения о действующей сертификации.

# 28. Экономика, BOM и риски поставки

## 28.1. Как считать стоимость, не выдавая её за факт

`Unit COGS = PCB/SoM + display + optics + camera + audio + enclosure + PSU + assembly + testing + packing + inbound logistics + warranty reserve + expected yield loss`. Отдельно `OPEX/call = signaling + TURN egress + media relay + push + logs + support + incident response`. Нельзя обещать фиксированную цену без коммерческих предложений поставщиков, состава деталей, MOQ, процента брака и расчёта фактического relay-трафика. Для каждого кандидата сохранять MOQ, условия оплаты, lead time, test evidence, EOL feasibility и lifecycle availability.

Экономический контроль нужен также для функций: аватар, нейронный inference в облаке и многовидовые дисплеи могут потребовать новых постоянных затрат. Оценивать не только себестоимость, но и стоимость повторного производства, доставки, возвратов и поддержки.

| Блок стоимости | Что измерить/получить | Риск | Решение |
| --- | --- | --- | --- |
| Оптический комплект | Котировки на 2–3 материала, покрытия, резку | Блики, брак, короткая доступность | Sample approval + alternate |
| Дисплей/контроллер | Цена, sustained luminance, интерфейс, lifespan | Burn-in / драйверы | Soak + vendor SLA |
| Вычислительный модуль | Фактическая encode/decode производительность, supply chain | Термодросселирование | Bench before purchase |
| Аудио | OEM микрофоны, AEC лицензия, акустическая механика | Echo | Double-talk test |
| Корпус и сборка | Инструмент, обработка, допуски, scrap | Несобираемая оптика | DFA/stack-up |
| Облачная инфраструктура | TURN egress, цена минут/канала, алерты | Cost explosion | Quota + audit |
| Гарантия | Возвраты, замена стекла/блока питания | Непредвиденный сервис | Pilot failure data |

## 32.1. Формальная процедура приёмки

Заказчик получает baseline сборки и документы; QA представляет отчёт исполнения P0/P1, список известных ошибок с severity, воспроизводимые тестовые записи и ссылки на требования; security и hardware safety подписывают релевантные части. Заказчик принимает этап протоколом G0/G1/G2 либо возвращает с конкретным списком блокирующих несоответствий. «Демонстрация работает» без тестовой матрицы не заменяет акт приёмки. Если P1 исключается, необходимо утверждённое отклонение с причиной, оценкой риска и планом закрытия.

# 35. Приложение C. Проверенные отправные источники и терминология
**Ссылки для проектирования; они не являются доказательством уже готового устройства.** Перед реализацией следует фиксировать версии документации, актуальные лицензии и применимость к выбранному стеку.

1. W3C, *WebRTC: Real-Time Communication in Browsers*: https://www.w3.org/TR/webrtc/ — модель PeerConnection и статистика.
2. Google AI Edge, *MediaPipe Image Segmenter for Android*: https://developers.google.com/edge/mediapipe/solutions/vision/image_segmenter/android — сегментация на Android, timestamps, асинхронный режим и ограничения потока кадров.
3. Google AI Edge, *Image Segmenter overview*: https://developers.google.com/edge/mediapipe/solutions/vision/image_segmenter — типы масок и режимы.
4. LiveKit, *Encryption overview*: https://docs.livekit.io/transport/encryption/ — E2EE возможности и ответственность за распределение ключей. Конкретную API реализацию необходимо сверять с установленной версией SDK.
5. LiveKit, *Get started with encryption*: https://docs.livekit.io/transport/encryption/start/ — варианты интеграции ключей и клиентов.
6. Регламенты ТР ТС 004/2011 и 020/2011, и иные применимые нормы ЕАЭС — официальные тексты и локальные требования уточнять у ответственного за соответствие. Само упоминание регламента не означает автоматической применимости к низковольтному изделию с внешним адаптером.

**Термины:** `AEC` — acoustic echo cancellation; `AV sync` — синхронизация звука и видео; `BOM` — перечень компонентов; `CAL` — калибровка; `E2EE` — end-to-end encryption; `EOL` — end-of-line; `EVT/DVT/PVT` — этапы hardware validation; `eye-box` — диапазон положений глаза, в котором изображение удовлетворяет согласованным условиям; `FPS` — частота кадров; `ICE/STUN/TURN` — механизмы установления медиасвязи; `P0` — обязательный приёмочный уровень; `RTC` — real-time communications; `SFU` — selective forwarding unit; `SoM` — system on module; `SLO` — service level objective; `TBD` — to be determined; `zero-copy` — передача GPU/codec буфера без лишнего копирования на CPU.

**Итоговая техническая позиция:** первый продукт — не «идеальная голограмма», а достоверная оптическая сцена с живым портретом и надёжной двусторонней связью. ТЗ считается основанием для разработки только после согласования неизвестных конструктивных решений и планов испытаний. Блокирующие требования не могут исчезнуть только потому, что создана красивая демонстрация.
